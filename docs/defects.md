# Разбор пяти дефектов

В `hw3-broken` было заложено пять намеренных дефектов. Ниже по каждому: в чём был, как проявлялся, как исправлен, каким числом подтверждается.

## Дефект 1. Данные попадали в git

**В чём был.** Файлы датасета не были исключены из git и не были поставлены под DVC. После `git add . && git commit` они оседали в истории репозитория.

**Как проявлялся.** `git log --stat` показывал крупные JSONL. `git ls-files data/` возвращал файлы данных. Проверка 1 в `tests/check.sh` была красной на пунктах про отслеживание файлов в data и про .gitignore.

**Как исправлен.**
1. В `.gitignore` добавлено `data/` и `metrics/*.json`, оставлен `!metrics/.gitkeep`.
2. Удалён кэш из индекса git: `git rm -r --cached data/ metrics/`.
3. Данные поставлены под DVC: `uv run dvc add data/raw.jsonl`.
4. Настроен локальный remote: `uv run dvc remote add -d local ../dvc_storage`.
5. В git закоммичены только `data/raw.jsonl.dvc`, `data/.gitignore`, `.dvc/config`, `metrics/.gitkeep`.

**Числом подтверждается.** `git ls-files data/` было N файлов, стало 0. Проверка 1 в `check.sh` - все четыре пункта зелёные.

## Дефект 2. Смена версии данных не пересчитывала пайплайн

**В чём был.** В `dvc.yaml` у стадии `collect` отсутствовала секция `params` (не было `- collect` и `- paths.raw`), а у стадии `clean` в `deps` не было `data/raw.jsonl`. Из-за этого DVC не видел, что смена `collect.version` в `params.yaml` должна тянуть пересчёт всей цепочки. Дополнительно у стадии `split` в `outs` не были указаны `data/val.jsonl` и `data/test.jsonl`.

**Как проявлялся.** После `uv run python scripts/set_version.py v2` и `uv run dvc repro` DVC отвечал, что stage collect didn't change, skipping, и что data and pipelines are up to date, хотя версия источника поменялась. Хэш `clean.jsonl` оставался одинаковым для v1 и v2. Проверка 4 в `check.sh` была красной.

**Как исправлен.**
1. В стадию `collect` добавлены `params: [collect, paths.raw]` и `metrics: [metrics/collect.json]`.
2. В стадию `clean` в `deps` первой строкой добавлен `- data/raw.jsonl`.
3. В стадию `split` в `outs` добавлены `data/val.jsonl` и `data/test.jsonl`.
4. В `params.yaml` добавлены `n_rows_v1` и `n_rows_v2`, а `collect.py` читает их через `cfg.get(f"n_rows_{version}", cfg.get("n_rows", 3000))`.

**Числом подтверждается.** Хэш `clean.jsonl` для v1 = 296416b4, для v2 = 350a37e5. Проверка 4 в `check.sh` стала зелёной.

## Дефект 3. Контаминация train/test

**В чём был.** Функция `row_split` в `src/split.py` делала случайный сплит по индексам строк, игнорируя `topic`. Один и тот же вопрос или его парафраз мог попасть и в train, и в test.

**Как проявлялся.** `scripts/check_contamination.py` находил пересечения между train и test. В `metrics/split.json` в секции `contamination` было ненулевое поле `group_overlap`. Проверка 5 в `check.sh` была красной.

**Как исправлен.** В `src/split.py` добавлена функция `group_split`, которая сначала группирует примеры по `normalize_group(topic)`, потом случайно перемешивает списки групп и раскидывает целые группы по сплитам. В `main()` вызов `row_split` заменён на `group_split(examples, cfg["ratios"], cfg["seed"], cfg["group_key"])`. Порог `contamination.threshold` оставлен равным `clean.near_dup.threshold` (оба 0.85).

**Числом подтверждается.** `group_overlap` было 9, стало 0. Пересечения по `id` и по тексту тоже 0. Проверка 5 в `check.sh` стала зелёной.

## Дефект 4. Near-dup не ловился

**В чём был.** В `src/clean.py` шаг 5 был заглушкой:

    # 5. TODO: сюда просится ещё один шаг дедупликации.
    near: set[int] = set()

Функция `near_duplicates` из `src/dedup.py` не вызывалась, `dropped_near_dup` всегда оставался 0. Точная дедупликация ловила только буквальные повторы, но не почти-дубли с переставленными вариантами ответа.

**Как проявлялся.** В `metrics/clean.json` поле `dropped_near_dup` было 0, хотя в источнике есть почти-дубли. Проверка 2 в `check.sh` подсовывала пару почти одинаковых вопросов и ждала, что хотя бы один удалится.

**Как исправлен.** В `src/clean.py` блок 5 заменён на вызов `near_duplicates(texts, shingle_words, num_perm, threshold)` из `src/dedup.py`. Функция возвращает список индексов, которые надо удалить. Параметры берутся из `clean.near_dup` в `params.yaml`: shingle_words = 4, num_perm = 64, threshold = 0.85.

**Числом подтверждается.** На тестовом наборе из `check.sh` `dropped_near_dup` было 0, стало 1. На реальных данных `dropped_near_dup` = 8, то есть 3000 строк превратились в 2992. Проверка 2 в `check.sh` стала зелёной.

## Дефект 5. Гейт diversity не падал на вырожденном наборе

**В чём был.** В `src/diversity.py` при нарушении порогов стадия печатала предупреждение и продолжала работу:

    if failed:
        print("diversity: предупреждение - " + "; ".join(failed))

Код возврата оставался 0, пайплайн проходил дальше. Вырожденный набор с одним system-промптом, одной темой и ответами одной длины спокойно доезжал до `split` и версионировался как валидный датасет.

**Как проявлялся.** Проверка 6 в `check.sh` подсовывала вырожденный набор из 1200 строк. Стадия `diversity` не падала. Проверка 7 на нормальном датасете тоже была нестабильна: из-за жёстких порогов (`min_groups: 50`, `max_group_share: 0.10`) она заворачивала собственный датасет студента.

**Как исправлен.**
1. `print` заменён на `raise SystemExit` с сообщением, какой именно порог нарушен и насколько.
2. Пороги адаптированы под синтезированную структуру тем: `min_groups: 50 -> 10`, `max_group_share: 0.10 -> 0.90`. Обоснование - в `docs/datasheet.md`.

**Числом подтверждается.** На вырожденном наборе код возврата был 0, стал 1, сообщение называет 4 нарушенных порога. На нормальном датасете проверка 7 зелёная: 2992 строки, 5 системных промптов, 10 групп, крупнейшая группа 74.5 процента, разброс длин p90/p10 = 1.7.
